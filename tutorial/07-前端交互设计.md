## 7.3 SSE 流消费：从 bytes 到 UI 状态

第 6 章已经介绍了后端如何生成 SSE 事件流。现在看前端如何消费它。

### 为什么不使用原生 EventSource？

浏览器原生的 `EventSource` API 有 3 个硬伤：

1. **只支持 GET 请求**：AI 对话需要 POST 发送消息体
2. **不支持自定义请求头**：无法携带 `X-Request-ID` 等追踪信息
3. **不支持 `AbortController`**：无法优雅地取消流

因此项目使用 `fetch` + `ReadableStream` 手动实现 SSE 解析：

```typescript
// frontend/src/services/api.ts
function _apiStreamInternal(
  path: string,
  options: { body: unknown; isJson: boolean },
  onEvent: (event: string, data: string) => void,
  onError: (err: Error) => void,
  onDone: () => void,
): AbortController {
  const controller = new AbortController();

  (async () => {
    try {
      const res = await fetch(`${BASE}${path}`, {
        method: 'POST',
        signal: controller.signal,
        headers: { 'Content-Type': 'application/json', 'X-Request-ID': nextRequestId() },
        body: JSON.stringify(options.body),
      });

      if (!res.ok) {
        onError(new ApiError(res.status, `HTTP ${res.status}`));
        return;
      }

      const reader = res.body?.getReader();
      if (!reader) {
        onError(new Error('No response body'));
        return;
      }

      await parseSSEStream(reader, onEvent, onDone, onError);
    } catch (err) {
      if (err instanceof Error && err.name === 'AbortError') return;
      onError(err instanceof Error ? err : new Error(String(err)));
    }
  })();

  return controller;
}
```

`AbortController` 是关键——它让用户可以点击"停止生成"按钮，立即中断流式传输，而不需要等待模型完成。

### SSE 解析器

```typescript
export function parseSSEStream(
  reader: ReadableStreamDefaultReader<Uint8Array>,
  onEvent: (event: string, data: string) => void,
  onDone: () => void,
  onError: (err: Error) => void,
): Promise<void> {
  const decoder = new TextDecoder();
  let buffer = '';

  return (async () => {
    while (true) {
      const { done, value } = await reader.read();
      if (done) break;

      buffer += decoder.decode(value, { stream: true });
      const lines = buffer.split('\n');
      buffer = lines.pop() || '';  // 最后一行可能不完整，留着下次拼接

      let currentEvent = '';
      for (const line of lines) {
        if (line.startsWith('event: ')) {
          currentEvent = line.slice(7).trim();
        } else if (line.startsWith('data: ')) {
          if (currentEvent) {
            onEvent(currentEvent, line.slice(6));
            currentEvent = '';
          }
        }
      }
    }
    onDone();
  })();
}
```

这里有一个容易被忽略的细节：`buffer = lines.pop() || ''`。SSE 流在 TCP 层面可能会将一个事件拆分成多个数据包，最后一行可能是不完整的。保留在 buffer 中，等下一个包到达时拼接，避免解析错误。

## 7.4 聊天界面的核心组件

### ChatArea：对话容器

`ChatArea` 是聊天界面的主容器，负责：
- 渲染消息列表（`MessageBubble` 列表）
- 控制自动滚动到底部
- 渲染思考面板（`ThinkingPanel`）
- 在底部固定渲染 `InputArea`

核心模式是"消息列表 + 固定输入区"的布局。输入区域使用 `shrink-0` 确保不被挤压。

### InputArea：输入交互核心

```tsx
// frontend/src/components/chat/InputArea.tsx（核心结构）
export function InputArea() {
  const input = useChatStore((s) => s.input);
  const setInput = useChatStore((s) => s.setInput);
  const streaming = useChatStore((s) => s.streaming);
  const sendMessage = useChatStore((s) => s.sendMessage);
  const stopStreaming = useChatStore((s) => s.stopStreaming);
  const currentRagMode = useChatStore((s) => s.currentRagMode);
  const toggleRagMode = useChatStore((s) => s.toggleRagMode);

  const handleSend = () => {
    if (!currentSessionId || streaming) return;
    if (!input.trim()) return;
    sendMessage(currentSessionId, input.trim());
    setInput('');
  };

  const handleKeyDown = (e: KeyboardEvent<HTMLTextAreaElement>) => {
    if (e.key === 'Enter' && !e.shiftKey) {
      e.preventDefault();
      handleSend();
    }
  };
  // ...
}
```

`Enter` 发送、`Shift+Enter` 换行是 AI 聊天应用的事实标准，本项目也遵循此规范。

### 输入区域的功能按钮

输入框上方有一排功能按钮：

- **上传文件**：点击打开文件选择器，支持 `.txt/.pdf/.docx/.xlsx/.md` 及图片格式
- **语音输入**：点击开始录音，使用 Web Speech API 转文字
- **联网搜索**：开关按钮，控制是否启用 Web 搜索
- **知识库模式**：三态切换 `off → auto → force`
- **模型选择器**（`ModelPicker`）：选择模型来源和具体模型

所有这些按钮的状态都存储在 `chatStore` 中，通过 Zustand 的 selector 机制实现精确重渲染——只有使用该状态的组件才会更新。

### MessageBubble：消息气泡

每条消息渲染为一个气泡，区分用户消息和 AI 回复的样式。对于 AI 回复，使用 `MarkdownRenderer` 进行渲染，支持代码高亮、数学公式、表格等。

AI 消息还支持：
- **复制**：一键复制整条回复
- **重新生成**：删除当前回复并重新请求
- **编辑**：编辑用户消息后截断后续消息（版本回退）

### MarkdownRenderer：内容渲染增强

AI 回复通常是 Markdown 格式。`MarkdownRenderer` 使用 `react-markdown` 进行渲染，并通过插件支持：

- 代码块语法高亮（`CodeBlock` 组件，支持一键复制）
- KaTeX 数学公式渲染（行内 `$...$` 和块级 `$$...$$`）
- 表格、列表、引用块等标准 GFM 元素
- `[N]` 引用角标的交互式渲染

### ThinkingPanel：思考过程展示

当模型支持 think mode 时，`ThinkingPanel` 折叠展示模型的推理过程（类似 DeepSeek-R1 的思维链），提供透明度但不干扰正常的回复阅读。

## 7.5 状态管理：Zustand 的优势

项目使用 Zustand 而非 Redux。两者对比：

```typescript
// Zustand——定义一个 store 只需要 create()
export const useChatStore = create<ChatState>((set, get) => ({
  input: '',
  streaming: false,
  thinking: '',
  ragSources: [],
  currentRagMode: 'auto',
  webSearchEnabled: false,

  setInput: (v) => set({ input: v }),
  setStreaming: (v) => set({ streaming: v }),
  toggleRagMode: () => set((s) => ({
    currentRagMode: s.currentRagMode === 'off' ? 'auto'
      : s.currentRagMode === 'auto' ? 'force' : 'off',
  })),

  sendMessage: (sessionId, message) => {
    // 业务逻辑 + API 调用
  },
  stopStreaming: () => {
    get().abortController?.abort();
    set({ streaming: false, abortController: null });
  },
}));

// 使用——极简
const input = useChatStore((s) => s.input);
const streaming = useChatStore((s) => s.streaming);
```

相比于 Redux 需要定义 action types、action creators、reducers、selectors、dispatch、Provider 包裹……Zustand 的代码量减少了 80% 以上，而功能完全对等。

### rAF 节流的 token 累加器

这是前端的一个关键性能优化：

```typescript
function createBufferedUpdate(update: (text: string) => void): (text: string) => void {
  let buffer = '';
  let scheduled = false;

  const flush = () => {
    scheduled = false;
    if (buffer) {
      update(buffer);
      buffer = '';
    }
  };

  return (text: string) => {
    buffer += text;
    if (!scheduled) {
      scheduled = true;
      requestAnimationFrame(flush);
    }
  };
}
```

大模型每秒生成 30-80 个 token，如果每个 token 都触发一次 `setState` + React 重渲染，浏览器会卡顿。`createBufferedUpdate` 利用 `requestAnimationFrame`（约 16ms 一帧）将同一帧内的所有 token 合并为一次状态更新——渲染频率从 80 Hz 降到 60 Hz，性能损耗几乎为零。

### Store 拆分策略

项目将状态拆分为四个独立的 store：

| Store | 职责 | 示例状态 |
|-------|------|---------|
| `chatStore` | 当前输入和流式状态 | input, streaming, thinking, ragSources |
| `sessionStore` | 会话列表和当前会话消息 | sessions[], currentSessionId, messages[] |
| `uiStore` | UI 全局状态 | sidebarOpen, settingsOpen, toast |
| `themeStore` | 主题偏好 | darkMode, accentColor |

拆分的好处：当 `streaming` 变化时，只有订阅了 `chatStore` 的组件会重渲染。`sessionStore` 中的消息列表不会因为流式状态的每次变化而重新计算。

## 7.6 文件上传交互

文件上传流程涉及前端多个状态的协调：

```tsx
// 选择文件
const handleFileSelect = (e: React.ChangeEvent<HTMLInputElement>) => {
  const file = e.target.files?.[0];
  if (!file) return;
  setPendingFile(file);  // 暂存，不立即发送
  e.target.value = '';
};

// 点击发送时执行上传
const doFileUpload = (file: File) => {
  if (!currentSessionId) return;
  const msgText = input || '请分析这个文件';
  setInput('');
  setPendingFile(null);
  sendFileMessage(currentSessionId, msgText, file);  // FormData + SSE
};
```

文件上传也是 SSE 流式传输（`apiStreamFormData`），与普通对话的区别仅在于使用 `FormData` 而非 JSON body。后端接收到文件后，会先发送一个 `file_info` 事件告知前端文件元数据（URL、大小、类型），然后才是正常的对话 SSE 事件流：

```typescript
const ctrl = apiStreamFormData('/chat/upload', formData,
  (event, data) => {
    if (event === 'file_info') {
      try { updateLastUserMessageFileInfo(JSON.parse(data)); } catch {}
    } else {
      onEvent(event, data);  // 其他事件正常处理
    }
  },
  onError, onComplete,
);
```

在前端，如果上传的是图片文件，用户消息气泡中会显示图片预览；如果是文档文件，则会显示文件类型图标和名称。

## 7.7 设置面板集成

`SettingsModal` 是一个集中的设置面板，管理：

- **系统提示词**：可编辑的 textarea，修改 AI 助手的角色设定

这些设置通过 REST API 读取和保存（`/api/settings`），所有变更立即生效并持久化到 `runtime_config.json`（见第 3 章）。


构建完成后，FastAPI 直接服务前端静态文件：

```python
# main.py
_fe_dist = os.path.join(os.path.dirname(__file__), "frontend", "dist")
if os.path.isdir(_fe_dist):
    app.mount("/assets", StaticFiles(directory=os.path.join(_fe_dist, "assets")), name="fe_assets")

    @app.get("/", response_class=HTMLResponse)
    async def index_react():
        fe_index = os.path.join(_fe_dist, "index.html")
        if os.path.isfile(fe_index):
            with open(fe_index, "r", encoding="utf-8") as f:
                return HTMLResponse(f.read())
        return HTMLResponse("Frontend not built. Run: cd frontend && npm run build")
```

这种部署方式将一个全栈应用打包为单一 Python 进程：
- API 路由（`/api/*`）由 FastAPI 处理
- 前端静态文件（`/assets/*`、`/`）由 `StaticFiles` mount 和 index.html 服务
- 无需 nginx、无需 Node.js 运行时、无需 Docker

用户只需一行命令：

```bash
python main.py
```

## 7.10 草稿自动保存

`useDraftAutoSave` hook 实现输入框草稿的自动保存：

```typescript
// hooks/useDraftAutoSave.ts
export function useDraftAutoSave(sessionId: string, input: string) {
  const saveTimer = useRef<number>();

  // 输入变化时防抖保存
  useEffect(() => {
    if (!sessionId) return;
    clearTimeout(saveTimer.current);
    saveTimer.current = window.setTimeout(() => {
      localStorage.setItem(`draft_${sessionId}`, input);
    }, 1000);
    return () => clearTimeout(saveTimer.current);
  }, [input, sessionId]);

  // 发送成功后清除草稿
  const clearDraft = (id: string) => {
    localStorage.removeItem(`draft_${id}`);
  };

  // 切换会话时加载草稿
  const loadDraft = (id: string): string => {
    return localStorage.getItem(`draft_${id}`) || '';
  };

  return { clearDraft, loadDraft };
}
```

使用 `localStorage` 是草稿保存的最简方案——不需要后端接口，不需要数据库，浏览器崩溃后也能恢复。

## 本章小结

- React + Vite + Zustand 构建了高性能的 AI 对话前端
- 手动 SSE 解析（`fetch` + `ReadableStream`）克服了原生 `EventSource` 的限制
- `createBufferedUpdate` 利用 rAF 将 token 累加优化渲染性能
- 四个 Zustand store 各司其职，避免不必要的重渲染
- 文件上传使用 FormData + SSE 混合流，先发送 `file_info` 再进入对话流
- `SettingsModal` 提供集中的配置管理
- 生产构建后由 FastAPI 直接服务，一个 Python 进程即全栈应用

至此，AI 智能助手的完整技术栈已经全部呈现。从基础骨架到数据层、从模型抽象到流式引擎、从前端交互到部署发布——你现在已经掌握了构建一个生产级 AI 对话应用的完整知识体系。
